# 고민 기록

> 기획 과정에서 무엇을 고민했고, 어떤 선택지 중에 무엇을 왜 골랐는지 남기는 문서
> 발표의 "기획 과정" 파트와 질의응답 준비에 사용

## 작성 방법

- 새 고민이 생길 때마다 **맨 아래 기록 목록에 항목 추가** (번호는 이어서)
- 항목마다: **고민 → 선택지 → 결정 → 이유 → 발표 포인트**
- 결정이 바뀌면 기존 항목을 지우지 말고, 새 항목에 "#N 결정 변경"으로 남기기 (바뀐 과정 자체가 고민의 흔적)
- 질의응답에 쓸 만한 내용은 아래 **예상 질문** 섹션에도 추가

---

## 기록 목록

### #1. 레벨을 사용자에게 보여줄 것인가 (v2)

- **고민:** 검사 결과로 Lv.1~4를 나누는데, "당신은 Lv.1입니다"는 위험군 사용자에게 낙인처럼 느껴질 수 있음
- **선택지:** ① 레벨 숫자 노출 ② 레벨은 내부에서만 쓰고 별자리로 표현
- **결정:** ② "카시오페이아자리부터 시작해볼까요?"처럼 출발점으로 표현
- **이유:** 평가받는 느낌 대신 여정의 시작으로 받아들이게 하기 위함
- **발표 포인트:** 위험군 사용자의 감정까지 고려한 설계라는 근거

### #2. 난이도 단계를 몇 개로 나눌 것인가 (v2)

- **고민:** 단계 간 간격이 크면 다음 단계로 못 넘어가고 이탈
- **결정:** 6단계 (집 안 → 집 앞 → 혼자 외출 → 사람 있는 곳 → 짧은 상호작용 → 대화·참여)
- **이유:** "집 밖에 나가기"와 "사람과 대화하기" 사이에 여러 중간 단계가 필요
- **추가 결정:** 같은 단계에 테마가 다른 별자리 2~3개를 두고 사용자가 선택 → 선택하는 재미는 남기고 난이도는 통제
- **발표 포인트:** 시작 단계는 1~4단계뿐이고, 5~6단계는 모두가 도달할 목표

### #3. 실패를 어떻게 다룰 것인가 (v2)

- **고민:** 퀘스트에 실패하면 좌절해서 앱을 떠날 수 있음
- **결정:** 별 밝기 3단계 (꺼진 별 / 희미한 별 = 시도함 / 밝은 별 = 완료), 연속 기록 끊김 같은 불이익 없음
- **이유:** 시도한 것 자체를 흔적으로 남겨서, 실패도 기록이 되게 함
- **발표 포인트:** 일반 습관 앱(스트릭, 벌금 등)과 반대되는 설계 → 차별성

### #4. 앱에만 의존하게 만드는 것 아닌가 (v2)

- **고민:** 앱 안 퀘스트로만 끝나면 실제 사회 복귀로 이어지지 않음
- **결정:** 공공 API(온통청년 정책·청년센터, 복지서비스, 1365 봉사) 연계, 청년센터에 단계별로 가까워지는 퀘스트
- **발표 포인트:** 앱이 목적지가 아니라 실제 지원으로 가는 징검다리

### #5. 심사 기준 검토 결과 AI가 없다는 걸 발견 (2026-11-17)

- **고민:** 예선 심사에서 AI 활용 25점 + 프로토타입 20점, 동점 시 AI 점수가 1순위인데 v1·v2 기획에 AI 기능이 전혀 없음
- **결정:** AI를 부가 기능이 아니라 핵심 흐름에 넣기로 함
- **기준:** "AI를 빼면 서비스가 돌아가지 않는가?"

### #6. 첫 AI 아이디어: 단계별 정책 분류·추천 (2026-11-17)

- **고민:** 정책 추천은 나이·지역·키워드 필터로도 되지 않나?
- **결정:** AI는 정책 설명을 읽고 **참여 부담 수준**(온라인 / 전화 / 방문 / 집단 참여)을 판단해 단계별로 분류
- **이유:** API에는 "이 정책이 얼마나 부담스러운가"라는 값이 없고, 설명 문장 속에 섞여 있음. 키워드 필터로는 관련 없는 정책이 섞이는 문제도 확인함
- **역할 분담:** 자격 조건(나이, 지역, 모집 상태)은 규칙으로 확실하게 거르고, AI는 부담 수준 분류와 쉬운 말 요약만 맡음
- **발표 포인트:** 키워드 필터 결과와 AI 분류 결과를 나란히 보여주면 AI가 필요한 이유가 바로 드러남

### #7. 정책을 퀘스트로 바꿀 것인가 (2026-11-17)

- **고민:** 정책을 단계별 퀘스트(정책 읽기 → 자격 확인 → 신청 → 상담 예약)로 바꾸면 AI가 핵심 흐름에 들어감. 하지만 **정책 퀘스트를 못 했을 때 좌절감**이 생기지 않을까?
- **검토한 위험:** 정책은 결과가 내 행동에만 달려 있지 않음 (탈락, 자격 미달, 대기, 마감). 고립 청년에게 "노력했는데 거절당했다"는 경험은 큰 타격
- **선택지:** ① 정책을 퀘스트로 전환 (선택형, 행동 기준 완료 등 보완 장치 필요) ② 추천까지만
- **결정:** ② **추천까지만**
- **이유:** 추천은 안 해도 아무 기록이 남지 않아서 좌절할 여지가 없음
- **보완:** 추천이 사용자 단계에 따라 달라지게 하고, 별자리를 완성해 단계가 오를 때마다 추천이 바뀌게 해서 핵심 흐름과 연결
- **발표 포인트:** "실패하면 상처받지 않나요?" 질문에 대한 답. 기능을 더하는 것보다 사용자를 다치게 하지 않는 쪽을 택했다는 근거

### #8. AI를 메인으로: 기능 5개 확정 (2026-11-17)

- **고민:** 정책 추천만으로는 AI가 여전히 핵심 흐름 밖에 있음. 핵심 흐름 중 매일 반복되는 구간은 "오늘 어떤 별을 켤까 → 수행 → 기록"
- **결정:** 반복 구간 전체에 AI를 넣음

| # | 기능                              | AI가 하는 일                                                                         |
| - | --------------------------------- | ------------------------------------------------------------------------------------ |
| 1 | 오늘의 별 추천 + 실패한 별 쪼개기 | 단계·시도 기록·오늘 날씨로 켤 별 선택. 희미한 별은 더 작은 퀘스트로 쪼개 다시 제안 |
| 2 | 체크인 → 마음 날씨 갱신          | 한 줄 일기를 읽고 날씨 갱신, 1번 추천에 반영                                         |
| 3 | 위험 신호 감지                    | 체크인·회고 문장에서 위기 표현 감지 시 109·전문기관 안내                           |
| 4 | 회고 맞춤 응원                    | 별을 켠 뒤 남긴 한 줄 회고에 맞춘 응원. 회고는 다음 추천에도 반영                    |
| 5 | 단계별 정책 추천                  | 정책을 참여 부담으로 분류, 사용자 단계에 맞춰 이유와 함께 추천                       |

```
[체크인 한 줄] ─AI→ 마음 날씨 갱신 + 위험 감지
        ↓
[오늘의 별 추천] ─AI→ 상태·기록에 맞춰 선택, 실패한 별은 쪼개기
        ↓
[수행 → 회고 한 줄] ─AI→ 맞춤 응원, 다음 추천에 반영
        ↓
[별자리 완성] ─AI→ 다음 단계에 맞는 정책 추천
```

- **역할 분담:** 첫 레벨 판정은 검증된 척도(UCLA, Mini-SPIN)로 하고, AI는 매일의 변화를 맡음
- **발표 포인트:** 매일 쓰는 모든 단계에 AI가 들어가 있음 → "AI가 핵심 기능에서 실제로 작동하는가" 항목의 근거

### #9. 4번 AI 기능: 사진 인증 확인 vs 회고 맞춤 응원 (2026-11-17)

- **선택지:** ① AI가 인증 사진이 퀘스트와 맞는지 확인 ② 퀘스트 후 한 줄 회고에 맞춤 응원
- **결정:** ② **회고 맞춤 응원**
- **이유:** 회고가 다음 별 추천의 데이터가 되어 AI 반복 흐름이 이어짐. 사진 검사는 사용자를 의심하는 느낌을 줄 수 있음
- **설계 원칙:**
  - 희미한 별(실패)에도 응원 ("현관까지 나간 것도 별 하나만큼의 일이에요")
  - 한두 문장으로 짧게, 과장된 칭찬과 "다음엔 ~해보세요" 같은 지시는 넣지 않음
  - 회고 입력도 3번 위험 감지를 거침
  - 생성 실패 시 미리 써둔 기본 응원 문구 사용

### #10. AI의 역할을 어디까지로 할 것인가 (2026-11-17)

- **고민:** AI가 길게 대화하면 상담사처럼 보이고, 위험군 대응 책임 문제가 생김
- **결정:** 짧게 듣고 별을 골라 주는 역할로 좁힘 (가칭 "별지기")
- **발표 포인트:** AI가 상담을 대신하지 않고, 필요한 순간에는 전문기관으로 연결한다는 점을 분명히 함

### #11. 심사 기준에 맞춰 v3 작성 (2026-11-17)

- **고민:** v2는 서비스 설계는 탄탄하지만 심사 기준의 여러 항목에 대한 근거가 문서에 없음
- **보완한 것:** AI 기능 5개와 한계 대응(AI 활용), 문제 근거·페르소나(문제 정의), 경쟁 서비스 비교(차별성), 효과 측정 지표(본선 해결 효과), 운영 주체·비용·개인정보(활용·확장), MVP와 데모 시나리오 갱신(프로토타입)
- **결정:** 심사 항목별로 어느 섹션이 답하는지 대응표를 v3 마지막에 둠
- **발표 포인트:** 대표 지표는 "쪼갠 별의 완료율"과 "실제 지원으로 연결된 비율". 데모에서 키워드 필터 vs AI 분류 비교를 보조 연출로 사용

### #12. 우리가 지향하는 방향: 사라지기를 바라는 앱 (2026-11-17)

- **고민:** 500자 소개에 핵심 기능은 다 들어갔지만, 우리가 어떤 방향을 지향하는지가 드러나지 않음
- **결정:** 지향점을 **"언젠가 필요 없어지기를 바라는 앱"**으로 정함
- **이유:** 마지막 별자리(청년센터 프로그램, 봉사 참여)를 완성한 사용자는 앱 밖에서 사람과 이어져 있어야 함. 앱이 목적지가 아니라 징검다리라는 기존 방향(#4)을 감정적으로 전달하는 문장
- **함께 보완:** 소개 글에 콘텐츠가 어떻게 보이는지(마음 날씨, 밤하늘의 별자리, 밝은 별·희미한 별, 도감, 더 큰 하늘이 열림) 추가
- **발표 포인트:** 오프닝이나 마무리 문장으로 사용. 대표 지표 "실제 지원으로 연결된 비율"과 연결하면 지향점이 숫자로도 보임

### #13. 이전 소개 글('나와' 버전)에서 무엇을 가져올 것인가 (2026-11-17)

- **고민:** 이전 소개 글에 지금 기획과 맞는 표현도 있고, 지금 설계와 충돌하는 요소도 있음
- **가져온 것:** "AI 기반 개인 맞춤형 사회화 퀘스트 앱"(한 줄 소개), 만보기 비유, "AI 에이전트", "활동 이력과 반응 분석", "자신만의 속도로 바깥세상과 연결"
- **뺀 것과 이유:**
  - **포인트·경험치:** 숫자로 평가하지 않는다는 원칙(#1)과 충돌. 별 밝기와 도감이 같은 역할을 함 → **#31에서 변경** (평가가 아니라 쌓이는 기록으로서의 포인트만 도입)
  - **주변 사용자와 함께하는 스몰톡 미션:** 지금 설계에 없고, 위험군 사용자가 낯선 사람을 만나는 안전 문제(악용, 거절 경험)가 큼. 사람과의 상호작용은 청년센터 프로그램·봉사처럼 기관이 있는 곳으로 연결하는 현재 방향을 유지
  - **"인간관계를 형성하고 유지하도록 돕는다":** 앱이 관계 유지까지 맡으면 "필요 없어지기를 바라는 앱"(#12)과 어긋남
- **미결:** 스몰톡처럼 사용자끼리 만나는 기능을 아예 뺄지, 안전한 형태로 다시 검토할지 → #14에서 "같은 하늘의 별"로 정리

### #14. 스몰톡 대신 "나만 그런 게 아니구나" 보여주기 (2026-11-18)

- **고민:** #13에서 스몰톡 미션은 뺐지만, "나와 같은 사람이 있다"는 감각은 외로움 해소에 도움이 됨. 토스 '주변 친구'처럼 대화 없이 주변 사용자 존재만 알려주면 어떨까?
- **검토한 위험 (토스 방식 그대로일 때):**
  - 실제 근처 사용자 표시 → "근처에 고립 청년 앱 사용자가 있다"는 것 자체가 민감정보, 좁은 동네에서는 누군지 특정 가능
  - 마스킹된 이름·캐릭터 → 아는 사람이면 알아볼 수 있음
  - 개인 단위 표시 → 다른 사람의 단계와 비교하며 "나만 뒤처졌다"는 감정
- **결정:** 개인이 아니라 **"같은 하늘의 별"**로 보여줌
  - 밤하늘 배경에 다른 사용자들의 별을 누구 것인지 모르게 희미하게 표시
  - 숫자는 모아서만: "오늘 우리 구에서 23명이 별을 켰어요", **"오늘 '현관 앞 5분 서 있기'를 18명이 시도했어요"**
- **원칙:** 이름·캐릭터·정확한 위치 표시 안 함(구 단위 이상) / 5명 미만이면 숫자 숨김 / 완료율·순위 없이 "시도한 사람 수"만 / 집계 포함 여부는 사용자가 선택
- **MVP:** 실제 사용자가 많아야 의미가 있어 "여유 있으면". 데모에서 쓰면 "예시 데이터" 표시
- **발표 포인트:** 상호작용 없이 동질감만 주는 설계. 희미한 별이 "나만 못 했다"가 아니라 "다들 이렇게 시도한다"가 됨. #13의 미결(사용자끼리 만나는 기능)은 이 방식으로 정리

### #15. 기술 스택: 비용 최소화 (2026-11-18)

- **고민:** 프로토타입을 먼저 만들 예정이고, 최대한 돈이 들지 않게 하고 싶음
- **결정:** AI는 **Gemini 무료 API** 사용
- **이유:** 프로토타입 단계에서 비용 0원, JSON 형식 출력(응답 스키마)을 지원해서 AI 기능 ①~⑤를 구현하기에 충분

  - 장점: 완전 무료, 외부 서비스 장애·일시정지·무료 등급 변경 걱정 없음

  - 주의: 팀원마다 DB 환경이 달라지지 않게 Docker Compose와 공통 스키마·초기 데이터 파일로 맞추기

  - PostgreSQL 쪽 장점: AI 결과 JSON 저장(JSONB)이 편하고, 나중에 배포가 필요해지면 Neon·Supabase로 연결 주소만 바꿔 옮길 수 있음

| # | 피드백 | 결정 |
| - | ------ | ---- |

| 6 | 위험 감지 설명 | "위험을 판별" → "위기 표현이 보이면 도움받을 곳을 안내". **"도움받을 곳" 메뉴를 항상 표시**. 안내 노출과 실제 상담은 구분해서 설명 |
| 7 | 인증 부담 | 자기 보고 기본, 사진 선택, 영수증 제외. GPS는 #21에서 결정 변경 |
| 8 | 모두를 청년센터·봉사로 | 마지막 별자리를 여러 개(청년센터 프로그램, 봉사, 원데이클래스·소모임 등) 두고 사용자가 선택 |
| 9 | 클릭 ≠ 참여 | 정책 지표는 "정보 확인 비율"로 설명, 참여는 사용자가 직접 기록한 것만 집계, 시연 데이터는 "예시" 표시 |

### #21. #20-7 결정 변경: GPS는 바깥 퀘스트의 기본으로 유지 (2026-11-18)

- **고민:** 피드백대로 인증 부담을 줄이려면 GPS도 빼야 하나? 하지만 GPS는 위치 기반 게임(포켓몬 고)에서 떠올린 아이디어로, "가면 별이 켜진다"는 재미가 바깥으로 나가는 동기가 됨
- **결정:** GPS를 **의심해서 확인하는 인증이 아니라 탐험 경험**으로 설계
  - 집 안 퀘스트: 자기 보고
  - 바깥 퀘스트: **GPS 도착 확인이 기본**. 목표 장소 근처(예: 100m)에 도착하면 별이 켜짐
  - 위치 권한 거부·신호 불량·실내 → **자기 보고로 바로 전환, 불이익 없음**
  - 사진은 선택(기록용), 영수증은 제외
- **활용:** 카카오 로컬 API로 가까운 공원·도서관·편의점·청년센터를 찾아 "오늘의 별" 장소로 제안. 청년센터는 "지도에서 찾기"(1단계) → "앞까지 가 보기"(4단계, 도착 확인)로 이어짐
- **개인정보:** 위치는 도착 확인 순간에만 읽음, 이동 경로·좌표·집 위치는 저장하지 않고 "도착함"과 장소 ID만 기록
- **참고 범위:** 위치 기반 게임의 메커니즘("장소에 가면 무언가를 얻는다")만 참고하고, 캐릭터·화면 구성·명칭은 가져오지 않음
- **MVP 변경:** GPS를 "여유 있으면" → **"꼭 구현"**. 2단계 "편의점 다녀오기"를 GPS 별로 바꿔 데모에 포함
- **시연 영향:** 브라우저 위치 기능은 HTTPS 또는 localhost에서만 동작 → 노트북은 개발자 도구로 위치 지정. 휴대폰으로 실제 걸으며 시연하려면 고정 HTTPS 주소가 필요해 **Vercel + Neon 배포를 검토할 이유가 커짐** (cloudflared 임시 주소는 카카오맵 도메인 등록 문제)
- **DB 반영:** `stars.verify_type`에서 receipt 제거, `stars.place_type`(목표 장소 종류) 추가, `star_attempts`에 `verify_method`, `place_id`, `place_name` 추가
- **발표 포인트:** 피드백을 무조건 따르지 않고, 우리가 지키고 싶은 경험(바깥으로 나가는 재미)은 지키면서 우려(부담·감시)를 설계로 해소함

### #22. 완료 버튼 "하늘의 별 따기"와 별에 담기는 기억 (2026-11-18)

- **아이디어(팀원 제안):** 미션을 마치고 누르는 버튼 이름을 **"하늘의 별 따기"**로. 보통 아주 어려운 일을 "하늘의 별 따기"라고 하는데, 집 앞에 나가는 것도 누군가에겐 그만큼 어려운 일일 수 있음. 자기가 정한 목표 하나를 했을 때 하늘에서 별 하나를 따다 담는 느낌이고, 나중에 별자리를 보며 "저 별은 내가 오랜만에 산책한 날 딴 거다"라고 떠올릴 수 있음
- **결정:** 채택
  - 완료 버튼: **"하늘의 별 따기"** → 밝은 별
  - 시도했지만 완료하지 못했을 때 버튼: **"손 뻗어 보기"** → 희미한 별. 별을 향해 손을 뻗은 것 자체가 기록이 됨 (#3 "시도도 흔적")
  - GPS 별은 목표 장소에 도착하면 "하늘의 별 따기" 버튼이 켜짐 (#21)
  - **별에 담기는 기억:** 도감·별자리에서 별을 누르면 그 별을 딴 날짜와 회고 한 줄을 보여줌 (예: "11월 20일 · 오랜만에 공원까지 걸었어요"). `star_attempts`의 날짜·회고를 그대로 사용해 DB 변경 없음
- **비유 통일:** 기존의 "별이 켜진다(점등)" 표현을 **"밤하늘의 별을 따서 → 내 별자리에 단다"**로 통일. 별자리 완성·도감과 자연스럽게 이어짐
- **이유:** 어려움을 인정하는 말이라 "자기 속도", "실패해도 괜찮다"는 원칙과 같은 방향. 숫자·포인트 없이도 기록이 개인의 기억으로 남아 성취감을 줌 (#13 포인트 제외와 일관)
- **발표 포인트:** 데모 마지막 장면으로 별을 눌러 그날의 기억을 보여주기. 서비스의 감정적 메시지를 한 장면으로 전달

### #23. 실제 날씨를 가져올 것인가 (2026-11-18)

- **고민:** 바깥 퀘스트(GPS 별)를 추천할 때 비·폭염·한파·미세먼지를 고려해야 하지 않나?
- **장점:** 비 예보가 있으면 가까운 도서관 같은 실내 장소를 함께 제안하는 등 AI ①의 "입력 → 판단 → 달라진 제안" 사례가 늘고 안전 면에서도 의미가 있음
- **우려:**
  - 화면에 "마음 날씨"와 실제 날씨가 함께 나오면 혼동 → 실제 날씨는 **"바깥 날씨"**로 이름·모양을 분명히 구분
  - 사용자의 선택을 덮어쓰면 안 됨 → 비가 와도 나가고 싶다면 존중, 정보로만 안내 (#20 원칙)
  - 개발 비용: 기상청 단기예보 API(data.go.kr)는 위경도 → 기상청 격자 좌표 변환 필요, 미세먼지는 에어코리아 API 별도
- **결정:** MVP에는 넣지 않고 **"여유 있으면" 1순위**. 범위는 "바깥 별 추천에 참고 + 작은 아이콘 표시"로 한정. API 키는 다른 공공 API와 함께 미리 신청
- **발표 포인트:** 확장 방안으로 "실제 날씨·대기질을 고려한 바깥 활동 추천" 언급 가능

### #24. 2차 기획 피드백: 순서 대신 선택지, 시도 후 다음 행동 (2026-11-18)

- **받은 피드백과 결정:** 모두 채택

| 고칠 부분 | 걸리는 점 | 결정 |
| --------- | --------- | ---- |
| 청년센터 방문과 문의 순서 | 운영시간·예약 여부를 알아야 나설 수 있는 사람도 있음. 별자리를 완성해야 센터를 볼 수 있는 것처럼 읽힘 | 정해진 순서를 없애고 **센터 상세 화면에 `문의 문장 준비하기`와 `앞까지 가 보기`를 나란히**. 첫날 지도에서 들어와도, 별자리 완성 후 추천으로 들어와도 같은 화면 |
| 시도한 별의 다음 행동 | `시도한 별 → 쪼개기`로 고정. "사람이 많아서"와 "비가 와서"는 다음 제안이 달라야 함 | 이유를 선택으로 묻고 **`더 작게 해 보기` · `다른 날 그대로 하기` · `여기서 마치기`** 중 사용자가 선택. AI ①이 이유에 맞는 행동을 제안 |
| GPS와 별이 켜지는 조건 | 센터 근처 도착만으로 문의·참여까지 기록되면 지표가 섞임 | 청년센터 흐름에서 **GPS가 켜는 별은 "앞까지 가 본 별" 하나뿐**. 위치를 안 쓰면 같은 화면의 **`직접 도착 기록`**으로 같은 별·같은 연출. 문의·참여는 사용자가 직접 기록 |
| 마지막 별자리의 선택권 | 세 가지 모두 외부 참여라 참여를 원하지 않으면 사실상 선택지가 없음 | **`지금은 여기까지`** 추가. 모은 별자리는 그대로 남고 원할 때 다시 이어감 |

- **GPS 범위 정리:** 편의점·공원 같은 일반 바깥 별의 GPS 도착 확인(#21)은 그대로. 이번 결정은 청년센터 흐름 안에서 "도착"과 "문의·참여"를 섞지 않는다는 것
- **희미한 별:** 이름만 바꿔도 실패 표시로 읽힐 수 있음 → 팀에서 결론 내리지 않고 사용성 테스트로 확인. "부담스럽나요?"가 아니라 설명 없이 보여 주고 **"이 별은 어떤 뜻으로 보이세요?"**라고 물음
- **대표 시연 변경:** 중심 장면을 **"센터 앞까지 갔는데 문을 열기는 어려워서 돌아왔어요"**로. 앞까지 가 본 별이 남고, AI가 "다음에 가기 전에 예약 없이 들러도 되는지 물어볼 문장을 같이 준비할까요?"라고 제안, 사용자는 초안만 저장하고 끝낼 수 있음
- **DB 반영:** `star_attempts`에 `stop_reason`(이유), `next_action`(smaller/retry/stop) 추가, `inquiry_drafts`(문의 문장 초안, 실제 문의는 `sent_at`에 직접 기록) 추가
- **발표 포인트:** 한 장면으로 세 가지가 드러남. 별을 모으는 재미(앞까지 가 본 별), 사용자의 선택권(초안만 저장하고 끝내도 됨), AI가 다음 행동을 조정하는 이유(회고에서 읽은 부담 → 문의 문장 제안). "여기서 마치기"·"지금은 여기까지"도 실패가 아니라 정상적인 선택으로 설계

### #25. 이전 버전 피드백 재검토: 이유별 조정, 재방문 가치, 성공 기준, 차별성 (2026-11-18)

- **배경:** v2~v3 시점에 받은 피드백을 다시 검토. 대표 사용자, 시작 단계, 단계 조건, 인증, 최종 목표, 지원까지의 이야기는 #20~#24에서 이미 해결됨. 남은 네 가지를 정리
- **결정:**
  1. **활동 조정 이유 확장 (수용):** 난이도뿐 아니라 취향·비용도 다룸. 이유에 "나랑 안 맞았어요", "돈이 들어서요" 추가, 다음 행동에 **`다른 별로 바꾸기`**(비슷한 난이도의 다른 활동) 추가. 예: 카페가 돈이 들어서 → 근처 공원·도서관
  2. **다시 찾는 이유 (수용) / 처음 들어오는 이유 (앱 기능으로는 다루지 않음):** 재방문 가치는 "오늘 뭘 하지를 정해 줌", "어려웠던 걸 기억하고 다음을 바꿔 줌", "뭐라고 말하지·어디 가지를 도와줌" 세 가지로 정리. 알림은 넣더라도 기본 꺼짐. **처음 들어오는 이유는 앱이 제공할 기능이 아니라 유입 경로(운영)의 문제**라고 판단 → 운영 주체(청년센터·지자체가 안내, B2G) 설명으로 답함
  3. **성공 기준 하나로 (수용):** 1순위 지표를 **"앱 밖 활동을 시도한 사용자 비율"**로 정함(손 뻗어 보기 포함). 보조는 "다음 행동을 고른 뒤 다시 시도한 비율"(AI 효과), "청년센터 행동별 기록"(지원 연결). 별 개수는 목표 지표로 쓰지 않음
  4. **차별성은 전체 경험으로 (수용):** "어려웠던 이유를 듣고 다음 행동을 다시 찾아, 실제 장소와 사람에게 이어 간다." 경쟁 서비스 비교표는 근거 확인 전 발표에 쓰지 않음
- **DB 반영:** `star_attempts.stop_reason`에 not_for_me, cost 추가, `next_action`에 swap 추가
- **발표 포인트:** 피드백의 총평("기능을 더하기보다 하나의 경험으로 연결")에 맞춰 새 기능 없이 기존 흐름만 보완함. 성공 기준을 "시도"로 둔 것이 서비스 원칙과 같은 방향이라는 점

### #28. AI 토큰·무료 한도를 아끼는 방법 (2026-11-19)

- **고민:** Gemini 무료 등급은 모델마다 하루 요청 수가 정해져 있음. 11/19 오전 `gemini-3.5-flash`가 **하루 20건 한도**를 넘겨 429가 났고, 한 사용자 흐름(체크인·추천·회고·문의 초안)에 4번 안팎 부르므로 시연 5번이면 멈춤. 정책 수집까지 AI로 하면 더 빨리 바닥남
- **결정:** "AI가 꼭 판단해야 하는 곳에만, 한 번 판단한 것은 저장해서 다시 쓰기"
- **사용자 요청에서 줄인 것**

| 방법 | 효과 |
| ---- | ---- |
| 오늘의 별 추천·정책 추천은 **하루 한 번 생성해 저장** | 새로고침·재방문은 AI 0회 (사용자당 하루 최대 1회) |
| 같은 날 활동 범위를 바꾸면 저장된 추천을 지금 범위로 **걸러서 재사용** | 바깥 → 집 안으로 바꿔도 재호출 없음 |
| 마음 날씨를 고쳐도 추천을 다시 만들지 않음 | 날씨는 난이도를 정하지 않으므로 (#20) |

### #30. 프로필 고도화: 고립·은둔 유형을 나눌 것인가 (2026-11-19)

- **고민:** 고립·은둔 청년은 "고립 vs 은둔", 생활 형태(독립거주–저소득형 / 건강·정서취약형 / 가족동거형, KIHASA 보건사회연구 46(1))로 나뉜다는 자료가 있음. 유형마다 필요한 지원이 다르니 프로필에서 유형을 판별하면 추천이 좋아질 것 같음. 그런데 v4에서 "검사 점수로 사람을 나누지 않는다"고 정함 (#20)
- **확인한 것:** 정부 정의에서 은둔은 고립이 깊어진 상태라 따로 떨어진 축이 아님. "고립 + 은둔이 가장 위험"은 근거를 찾지 못함. "유형별 지원 방향"은 논문에서 확인하지 못함 (우리가 정리한 것). 고립·은둔 청년의 약 70%가 가족과 동거

- **이유:**
  - 유형 이름은 낙인이 될 수 있고(#1), 짧은 질문으로 유형을 판별할 근거도 없음. 답 그대로 쓰면 같은 효과를 내면서 사용자가 언제든 고칠 수 있음
  - 소득은 직접 묻지 않고 "생활비·일자리가 필요해요"로 방향만. 정확한 소득은 정책 자격 확인이 필요한 사람만 따로

- **발표 포인트:** "연구에서 고립·은둔 청년의 유형이 나뉜다는 걸 확인했지만, 저희는 사람에게 유형 이름을 붙이지 않았습니다. 유형을 가르는 요소를 선택 질문으로만 묻고, 그 답은 어떤 지원 정보를 먼저 보여 줄지에만 씁니다." 정책 자격은 AI가 아니라 규칙으로 판단하고, 판단할 수 없으면 확인할 조건으로 보여 줌

  - **유성 번호 = 서버 시각 ÷ 16초:** 서버가 유성을 하나씩 발급하면 요청이 늘고 상태를 들고 있어야 함. 대신 "16초마다 1개"로 정해 두면 화면과 서버가 계산만으로 같은 유성을 가리킴. 화면은 `GET /api/points`의 서버 시각으로 기기 시계 차이를 맞춤. 떨어진 지 60초 안의 유성만 받아 지난 번호를 몰아 보내는 것을 막음
  - **유성 하루 20개 한도:** 한도가 없으면 화면을 켜 두기만 해도 시간당 225점이 쌓여, 앱 밖 행동(별)과 체크인보다 "화면 붙잡고 있기"가 더 큰 점수가 됨 → "언젠가 필요 없어지기를 바라는 앱"(지향점)과 반대. 하루 최대 20 < 체크인 100 < 별자리 하나(30~160)가 되게 함
  - **받지 못한 유성은 오류가 아니라 200 + `reason`:** 이미 받은 유성·한도·지난 유성에 오류 화면을 띄우면 실패 경험이 됨(#3). 화면은 +1만 띄우지 않으면 됨
  - **체크인 포인트는 체크인과 따로 저장:** 한 문장으로 묶으면 포인트 저장 실패(예: Neon에 변경 SQL 적용 전)가 체크인 저장까지 실패시켜 추천 흐름이 끊김. 체크인을 먼저 저장하고 포인트는 실패해도 `null`로만 응답
  - **위험 신호가 있는 체크인도 +100:** 힘든 날 마음을 적어 준 것도 한 걸음. 위험도에 따라 포인트를 다르게 주면 솔직하게 쓰지 않게 됨
- **원칙과 충돌하지 않게:** 연속 체크인·체크인 일수는 응답에도 넣지 않음(연속 기록 압박 없음, #31). 감점·초기화 없음. 다른 사람과 비교 없음
- **남은 고민:** 하루 한도(20)와 간격(16초)은 시연해 보고 조정 (`web/src/lib/points.ts` 숫자만 바꾸면 됨, 이미 받은 포인트는 그대로). 서로 다른 유성을 동시에 보내면 한도를 최대 6개 넘을 수 있음 (같은 유성 중복은 없음)

- **"에이전트 3개"는 모델 3개가 아니라 역할 3개:** 지시문·입력·할 수 있는 일이 다름. 같은 모델끼리는 같은 실수를 하기 쉬워서, 확인 가능한 사실은 규칙으로 검증하고 승인만 다른 모델(`gemini-3.5-flash`)로. 승인까지 오는 건 하루 몇 건이라 상위 모델의 하루 20건 한도로 충분
- **안전장치:** AI는 판단만 하고 실제 수정은 정해 둔 칸(지역·이용 가능·방식·난이도·나이)과 칸마다 정해 둔 SQL만 실행 → 자유 입력에 "제목을 바꿔" 같은 지시가 와도 막힘. AI가 실패하면 판정 없음·승인 안 함(안전한 쪽). 자유 입력에도 위기 표현 규칙

### #39. 신청 도우미 챗봇: 무엇을 AI에 맡기고 무엇을 규칙으로 할까 (2026-11-21, 구현)

  - 오늘(한국 날짜) 가장 최근 체크인만 참고. 정책 추천은 하루 한 번 저장이라, 필요한 것이 생긴 체크인은 오늘 저장된 추천을 지워 다음에 새로 만들게
  - 화면: 맞춤 추천 위에 "오늘 체크인을 참고했어요 · 돈·일" + **[오늘은 참고하지 않기]**(오늘 체크인의 필요를 비우고 추천을 다시 만듦, 내일부터는 다시 참고)
  - 정책 쪽 AI에는 체크인 문장을 보내지 않음 (필요한 것 이름만 기존처럼)
- **구조:** 체크인 지시문·응답 형식을 라우트에서 `@/lib/checkin-ai`로 옮김 (동작은 그대로, needs만 추가). 위험 감지 평가가 실제와 같은 지시문을 쓰기 위함 (#48)
- **DB:** `checkins.needs TEXT[]` (`db/migrations/20261122_checkin_needs.sql`, 여러 번 실행 안전). Neon 적용은 합친 뒤
- **검증:** 정책 **60/60** (새 9개: 정해 둔 말만·중복 없이, 위험이면 비움, AI 실패면 없음, 어제 체크인은 안 씀, 오늘 체크인 → 점수에 합쳐짐, 추천 응답 표시(새로·다시 쓰기), 참고하지 않기, DB 장애). 프로필 50/50·포인트 44/44·별 API 81/81 그대로. HTTP 19/20 — 실패 1건("다른 세션 총점 0")은 PR #24(체크인 +100점) 뒤로 기대값이 낡은 기존 테스트, 이번 변경과 무관
- **실제 AI 확인 (GMS gpt-4o-mini, 8문장):** 필요한 것 8/8 맞음 (월세 걱정·면접 탈락 → 돈·일, 잠 못 잠 → 건강, 엄마와 다툼 → 가족, 며칠째 말 안 함 → 사람, 일상 2개 → 없음, "돈도 없고 다 끝내고 싶어요" → 위험이라 비움). 다만 "월세 걱정", "잠 못 잠"을 위험 주의(caution)로 봄 → 칸을 늘린 것이 위험 판단에 영향을 주는지 #48 평가에서 확인

## 예상 질문과 답변

**Q. AI 없이 필터로도 정책 추천은 되지 않나요?**
A. 자격 조건은 필터로 거릅니다. 하지만 "이 정책이 은둔 청년에게 얼마나 부담스러운가"는 API에 없는 값이라 설명 문장을 읽고 판단해야 합니다. (#6)

**Q. 퀘스트에 실패하면 오히려 상처받지 않나요?**
A. 끝까지 못 했어도 "손 뻗어 보기"로 희미한 별이 남고 불이익이 없습니다. 돌아온 이유를 고르면 AI가 더 작게, 다른 날, 다른 활동 중 맞는 다음 걸음을 제안하고, 여기서 마쳐도 됩니다. 결과를 통제할 수 없는 정책은 일부러 퀘스트로 만들지 않았습니다. (#3, #7, #24, #25)

**Q. 앱에만 의존하게 되지 않나요?**
A. 청년센터 정보와 정책은 단계와 관계없이 언제든 볼 수 있고, 센터 상세 화면에서 문의 문장 준비나 앞까지 가 보기를 고를 수 있습니다. 앱은 목적지가 아니라 실제 지원으로 가는 징검다리입니다. (#4, #20, #24)

**Q. 위험한 사용자는 어떻게 대응하나요?**
A. "도움받을 곳" 메뉴를 언제든 볼 수 있게 두었고, 체크인과 회고에서 위기 표현이 보이면 규칙과 AI로 109·전문기관을 안내합니다. 감지가 완벽할 수는 없어서 "판별"이 아니라 "안내"로 설계했고, 안내를 본 것을 상담을 받은 것으로 집계하지 않습니다. AI는 상담을 대신하지 않습니다. (#10, #20)

**Q. 사용자가 앱을 떠나는 게 목표면 지속 가능한가요?**
A. 운영 주체는 지자체·청년센터(B2G)이고, 이들에게 성과는 앱 사용 시간이 아니라 실제 지원으로 연결된 청년 수입니다. 사용자가 졸업할수록 서비스의 가치가 증명됩니다. (#12, v3 9장)

**Q. 레벨을 왜 보여주지 않나요?**
A. 위험군에게 숫자 레벨은 낙인이 될 수 있어서 별자리 출발점으로 표현했습니다. 지금은 시작 단계도 검사 점수가 아니라 사용자가 직접 답한 "오늘 할 수 있는 활동 범위"로 정합니다. (#1, #20)

**Q. 검증된 심리 척도를 왜 시작에 쓰지 않나요?**
A. 외로움·사회불안 척도는 앱의 활동 단계나 외출 가능 범위를 정하도록 만든 도구가 아니라서, 점수를 단계로 바꿀 근거를 설명할 수 없었습니다. 그래서 시작은 사용자에게 직접 묻고, 척도는 원하는 사람만 4주마다 응답해 변화를 보는 용도로 남겼습니다. (#20)

**Q. 단계를 왜 잠가 두나요? 각자의 속도라면서요.**
A. 추천은 단계를 기준으로 하지만, 별자리를 다 채우지 않아도 바로 위 단계는 직접 열 수 있고, 청년센터·정책 같은 외부 정보는 처음부터 언제든 볼 수 있습니다. 갑자기 너무 어려운 활동으로 뛰어 실패하는 것만 막는 안내 장치입니다. (#20)

**Q. GPS로 위치를 확인하는 건 감시 아닌가요?**
A. GPS는 의심해서 확인하는 인증이 아니라 "도착하면 별이 켜지는" 탐험 경험입니다. 위치는 도착을 확인하는 순간에만 읽고, 이동 경로·좌표·집 위치는 저장하지 않습니다. 위치를 쓰기 싫거나 못 쓰면 자기 보고로 바로 바꿀 수 있고 불이익도 없습니다. (#21)

**Q. 결국 모두를 청년센터로 보내려는 건가요?**
A. 마지막 별자리는 청년센터 프로그램, 봉사, 원데이클래스·소모임 중에서 고를 수 있고, "지금은 여기까지"를 고를 수도 있습니다. 모은 별자리는 그대로 남고 원할 때 다시 이어갑니다. 청년센터도 문의 준비와 앞까지 가 보기를 순서 없이 고르고, 참여 여부는 사용자가 정합니다. AI는 문의 문장 초안처럼 문턱을 낮추는 일만 돕습니다. (#20, #24)

**Q. 실패하면 무조건 더 작게 쪼개나요?**
A. 아닙니다. 왜 돌아왔는지를 선택으로 묻고, "더 작게 해 보기", "다른 날 그대로 하기", "여기서 마치기" 중 사용자가 고릅니다. 사람이 많아서 돌아왔다면 더 작은 걸음을, 비가 와서 돌아왔다면 같은 별을 다른 날에 하자고 AI가 이유에 맞춰 제안합니다. (#24)

**Q. 서비스가 잘됐다는 건 무엇으로 판단하나요?**
A. 1순위는 "앱 밖 활동을 시도한 사용자 비율"입니다. 완료나 참여가 아니라 시도를 세는 이유는, 저희가 풀려는 문제가 "첫걸음을 떼기 어렵다"이기 때문입니다. 별 개수는 쉬운 별만 모아도 커져서 목표로 쓰지 않습니다. (#25)

**Q. 별 모으기 말고 사용자가 다시 찾을 이유가 있나요?**
A. "오늘 뭘 하지?"를 한 줄 체크인으로 정해 주고, 어려웠던 이유를 기억해 다음 행동을 바꿔 주고, "뭐라고 말하지?", "어디 가지?"를 문의 문장과 근처 장소로 도와줍니다. 처음 알게 되는 경로는 청년센터·지자체가 직접 닿기 어려운 청년에게 안내하는 운영 방식으로 답합니다. (#25, v3 9장)

**Q. 다른 서비스와 뭐가 다른가요?**
A. 기능 하나하나보다 경험 전체가 다릅니다. 어려웠던 이유를 듣고, 그 이유에 맞춰 더 작게, 다른 날, 다른 활동으로 다음 행동을 다시 찾고, 그것을 실제 장소와 사람에게 이어 갑니다. (#25)

**Q. GPS로 센터 근처에 가면 참여한 걸로 치나요?**
A. 아닙니다. GPS가 켜는 별은 "앞까지 가 본 별" 하나뿐이고, 문의와 참여는 사용자가 직접 기록할 때만 남습니다. 도착과 참여를 섞지 않아야 지표도 정직해집니다. (#24)

**Q. 배포까지 했는데 개인정보는 어떻게 하나요?**
A. 이번 배포는 시연용이고 실사용은 하지 않습니다. 화면에 "실제 개인정보를 입력하지 마세요"라고 안내했고, 실서비스로 전환하면 입력을 학습에 쓰지 않는 유료 AI 등급, 로그인, 동의 절차를 추가합니다. (#27)

**Q. 체크인을 민감정보라고 하면서 무료 Gemini에 보내도 되나요?**
A. 프로토타입에서는 실제 사용자 데이터 없이 테스트 문장만 사용했습니다. 실제 운영 시에는 입력을 학습에 쓰지 않는 유료 등급이나 Vertex AI로 바꿉니다. 지금도 AI에는 이름 등 식별 정보 없이 한 줄 문장만 보내고, 사용자는 언제든 기록을 삭제할 수 있습니다. (#15, v3 7장)

**Q. AI가 위험 신호를 놓치면 어떡하나요?**
A. 키워드 규칙을 먼저 적용하고 AI 판단과 합쳐 더 위험한 쪽을 택합니다. 직접 표현뿐 아니라 "나 없으면" 같은 간접 표현도 규칙에 넣었고, AI 호출이 실패하면 힘들다·우울하다 같은 표현만 있어도 안내를 보여줍니다. 앱은 상담을 대신하지 않고, 위험할 때 109와 전문기관으로 연결하는 것이 역할입니다. (#10, #19)

**Q. AI가 마음 상태를 잘못 판단하면요?**
A. 날씨는 참고 기록일 뿐이고, 오늘 할 활동의 난이도는 사용자가 직접 고른 "오늘은 어떤 활동이 괜찮을까요?"를 우선합니다. 날씨도 언제든 고칠 수 있습니다. AI가 고른 날씨와 사용자가 고친 날씨를 따로 저장해 사용자가 AI 판단을 조정한 비율을 확인하고 프롬프트 개선에 씁니다. 고치지 않았다고 AI가 맞았다고 보지는 않습니다. (#19, #20)

**Q. 시연 중에 AI나 서버가 멈추면요?**
A. 모든 AI 호출은 실패 시 기본값으로 대체되고, DB 저장이 실패해도 화면 흐름과 위험 안내는 이어지도록 만들었습니다. 데모용 AI·공공 API 응답도 미리 저장해 두었습니다. (#16, #19)

**Q. 무료 AI로 시연 중에 한도가 끝나면요?**
A. AI는 판단이 꼭 필요한 곳에만 쓰고, 한 번 판단한 결과는 저장해서 다시 씁니다. 추천은 사용자당 하루 한 번, 정책 분류는 미리 한 번(새로 바뀐 정책만 다시)이라 평소 호출이 적습니다. 그래도 한도가 끝나거나 응답이 늦으면 규칙으로 고른 기본값으로 바로 넘어가 화면은 멈추지 않습니다. (#16, #28)

**Q. 고립형·은둔형처럼 사용자 유형을 나누나요?**
A. 나누지 않습니다. 연구에서 생활 형태별 유형이 나뉜다는 것은 확인했지만, 유형 이름은 낙인이 될 수 있고 짧은 질문으로 판별할 근거도 없습니다. 대신 기댈 사람이 있는지, 누구와 지내는지, 요즘 무엇이 필요한지를 선택 질문으로 묻고, 그 답은 어떤 지원 정보를 먼저 보여 줄지에만 씁니다. 별 난이도에는 쓰지 않습니다. (#30)

**Q. 소득이나 취업 상태 같은 민감한 정보를 받나요?**
A. 정책 자격을 미리 걸러 받고 싶은 사람만 선택으로 알려 줍니다. 이 정보는 AI에 보내지 않고 규칙으로만 비교하며, 확실히 맞지 않는 정책만 추천에서 뺍니다. 판단할 수 없는 조건은 "원문에서 확인할 조건"으로 보여 주고, 언제든 한 번에 지울 수 있습니다. (#30)

**Q. 애니메이션이 많으면 오래된 휴대폰에서 느리지 않나요?**
A. 움직임은 기기가 가볍게 처리하는 방식(위치·투명도 변화)만 쓰고, 입자 수를 고정했습니다. 화면 전환은 브라우저 기본 스크롤처럼 손가락을 따라 넘어가게 했고, "동작 줄이기" 설정을 켠 사용자에게는 움직임을 모두 멈춥니다. (#29)
